# BasketLens verification protocol

## What tests prove

All packaged fixtures under `tests/` are deliberately synthetic. Automated checks validate schema normalization, cleaning, invoice conflict policy, transaction/basket arithmetic, time ordering, candidate selection, association metrics, rule recommendation, source-independent artifact integrity, and CLI argument handling. They cannot establish conclusions about UCI Online Retail II until the official workbook is processed.

Two optional integration modules only run when their real runtime libraries are installed:

- `test_fpgrowth_optional.py`: executes actual mlxtend FP-Growth on fixed synthetic baskets, confirms a 2-to-1 rule and numerical agreement with the pairwise baseline.
- `test_streamlit_optional.py`: runs the actual Streamlit script without a graphical browser, checking empty-data and generated-data cases. This does not replace interactive mobile, keyboard, and browser QA.

## First full dataset run

1. Verify Python and package availability with `python -m basketlens.cli doctor`.
2. Download the original file from the cited UCI page or run `python -m basketlens.cli download`.
3. Check the workbook's provenance and ensure the local source is `data/raw/online_retail_II.xlsx`.
4. Run `python -m basketlens.cli build --algorithm pairwise`. This establishes the independently calculated 1-to-1 baseline.
5. Run `python -m basketlens.cli verify`. Save its output with the build settings.
6. Run `python -m basketlens.cli build --algorithm fpgrowth`. The model should include all eligible 1-to-1 pairs, subject to identical thresholds, plus qualifying 2-to-1 rules.
7. Run `python -m basketlens.cli verify` again, then check counts, excluded rows, coverage fractions, holdout behaviour and rule stability.
8. Launch `streamlit run app/streamlit_app.py` and test narrow and wide layouts, product search, country filter, graph, both downloads, no-data mode, empty rules, and keyboard navigation.
9. Before publishing: ensure dataset attribution, no customer identifiers in outputs, no secrets, a validated source hash, and clearly labeled observational limitations.

If legitimate source invoices contain conflicting dates or countries, the default build fails closed. Only after examining the frequency and causes, explicitly run `--inconsistent-policy quarantine`. The output will then exclude all affected invoices and report the loss of rows.

## Required quality gate

```bash
python -m pytest -q
python -m compileall -q src app tests
python -m basketlens.cli verify
python -m pip check
```

The `verify` command requires a processed artifact directory. Without a real workbook, it can only validate a deliberately labeled synthetic fixture generated by tests.

## Evidence checklist

- [ ] Official workbook downloaded and source SHA-256 recorded
- [ ] Full two-sheet row count checked and missingness/exclusions reviewed
- [ ] All source invoice conflicts resolved or quarantined with explicit policy
- [ ] Full-data pairwise run completed and validated
- [ ] Full-data FP-Growth run completed and validated
- [ ] Candidate SKU/basket coverage reviewed and exclusions explained
- [ ] Holdout rule diagnostics and confidence bounds reviewed
- [ ] Local Streamlit research UI tested at desktop/mobile widths if the analytical workbench is in scope
- [ ] Exact-head CI and Vercel guest/source SHA checks verified after approved changes
- [ ] No sensitive data, credentials, or raw retail data committed
- [ ] Repository, release, and screenshots match actual verified functionality

Do not claim sales or profit uplift from historical co-occurrence. Product trials would require prospective randomized experiments.

## CI full-source quality gate (selective)

The GitLab `real_dataset_audit` runs automatically for analytics/CI/research changes, but is manual and non-blocking on docs/presentation-only MRs. Other unit, frontend, UI smoke and hosted Vercel jobs still run. When invoked, the full audit downloads the original UCI workbook, checks contradictions (83 source invoices identified during the initial real-data run), rejects excessive quarantine loss above 1%, rebuilds pairwise and FP-Growth and validates parity. A green pipeline without that executed job does **not** establish a new full-UCI audit. Inspect actual job status and source scope.

## Browser-level release smoke

When a full UCI audit is run, Chromium exercises the **local research Streamlit workbench** with real generated artifacts. This is distinct from public deployment QA. GitLab `public_ui_smoke` checks the Vercel frontend using synthetic UI fixtures across five widths; `hosted_portfolio_smoke` independently checks the live unauthenticated Vercel alias and, on main, validates the `/release.json` GitLab commit identity. None of these are a full accessibility audit or a measured sales experiment.


### Public exhibit release gate

1. Build the full-data FP-Growth analysis from the official UCI workbook.
2. Validate pairwise and FP-Growth parity, temporal holdout and arithmetic.
3. Run \`python scripts/build_public_demo.py --input .audit/fpgrowth --output data/public_demo\`.
4. Load the produced \`basketlens_public_v1.b64\` with
   \`basketlens.public_demo.load_public_demo\` and verify its checksum.
5. Check that all public tables exclude invoice numbers, customer identifiers
   and raw transactions. Product/catalog and country facts are aggregated.
6. Run Chromium browser smoke tests in public-only mode on desktop and mobile.
7. Copy only the checked public bundle into the repository. Never commit raw UCI
   XLSX, invoice-level processed CSV, temporary audit folders or credentials.
8. Verify GitLab/GitHub reviewed file parity and the public Vercel URL, including exact GitLab main `gitSha` and exhibit fingerprint in `/release.json`. Streamlit Cloud is not an active public target.
